# RAG 系统下一阶段优化计划

> 日期：2026-08-19
> 状态：待执行
> 目标：整体分数从 71.8% 提升到 80%+

---

## 背景

经过本轮优化，系统从 65.6% 提升到 71.8%。主要改进来自检索层（A/B类从 50-60% 提升到 80-90%+）。但 H类（前提纠偏）和 I类（拒答边界）仍有明显短板，C类（跨文档对比）虽有提升但仍是弱项。

下一阶段的重点是：**在保持 A/B 类高分的同时，提升 H/I/C 类的表现**。

---

## 阶段一：H类错误前提纠偏（预计 2-3 天）

### 问题分析

**典型案例**：
- Q50："2024年混凝土机械收入同比增长了多少？" → 实际可能下降了，LLM 没有纠正
- Q51："为什么连续三年加大研发投入？" → 实际在减少，LLM 纠正了数据但没有明确否定前提
- Q54："海外覆盖国家数量比2023年增加了多少？" → 实际可能减少了

**根因**：
1. LLM 倾向于"回答问题"而不是"验证前提"
2. 检索到的 chunks 可能没有直接的"反面证据"
3. Prompt 中的纠偏指令不够明确

### 改进方案

#### 方案 A：Prompt 强化（风险低，效果有限）

在 SYSTEM_PROMPT 的"前提验证"部分增加更明确的指令：

```python
"## 前提验证（高优先级）\n"
"当用户问题包含趋势性断言（如「增长」「增加」「加大」）时：\n"
"1. 必须从检索内容中找出实际的数值变化\n"
"2. 如果实际趋势与用户断言相反，回答的第一句必须是明确否定\n"
"3. 否定格式：「需要纠正的是，根据文档，[指标]实际上是[实际趋势]，而非[用户断言]」\n"
"\n"
"示例：\n"
"用户问：「为什么研发投入连续三年加大？」\n"
"文档显示：研发投入 61亿→55亿→52亿（实际在减少）\n"
"正确回答开头：「需要纠正的是，根据文档，公司的研发投入实际上是连续三年减少的（61亿→55亿→52亿），而非加大。」\n"
"错误回答：「公司近三年研发投入分别为61亿、55亿、52亿...」← 没有明确否定前提\n"
```

**风险**：规则太强可能导致 LLM 过度纠偏（把正确前提也否定）

#### 方案 B：反面证据检索（风险中，效果好）

在检索层增加"反面证据"检索：

```python
def _search_counter_evidence(query: str, chunks: list[RetrievedChunk]) -> list[RetrievedChunk]:
    """当 query 包含趋势断言时，主动检索反面证据。"""
    trend_keywords = {"增长", "增加", "加大", "提升", "扩大"}
    if not any(kw in query for kw in trend_keywords):
        return []
    
    # 构造反面查询
    opposite_query = query.replace("增长", "下降").replace("增加", "减少")
    # 用反面查询做检索
    counter_chunks = retrieval_engine.retrieve(opposite_query, ...)
    return counter_chunks
```

**优点**：确保检索到反面证据，LLM 更容易纠偏
**缺点**：增加检索延迟和复杂性

#### 方案 C：两阶段回答（风险低，效果中）

修改 prompt，要求 LLM 先验证前提再回答：

```python
"## 回答流程（复杂问题）\n"
"1. 在 <think> 中先验证问题前提：\n"
"   - 用户假设了什么趋势？\n"
"   - 检索内容是否支持这个趋势？\n"
"   - 如果不支持，需要明确否定\n"
"2. 在 <answer> 中：\n"
"   - 如果需要否定前提，第一句必须是明确的否定陈述\n"
"   - 然后提供正确的数据和分析\n"
```

### 推荐方案

**短期**：方案 A + C（prompt 强化 + 两阶段回答）
**长期**：方案 B（反面证据检索）

### 验证标准

- Q50/Q51/Q54 得分从 1分提升到 2-3分
- H类整体从 1.40/3 提升到 2.0+/3
- 不引入新的失败案例（如过度纠偏）

## 阶段二：I类拒答边界（预计 1-2 天）

### 问题分析

**典型案例**：
- Q55：问"2025年新能源产品收入" → 系统回答了 2024 年的数据（40.25亿元）
- Q59：问"H股总市值" → 系统用发行价×股数计算了错误的市值

**根因**：
1. 检索到了相关但不匹配的数据（2024 年数据 vs 2025 年问题）
2. LLM 没有意识到年份不匹配
3. LLM 试图"帮助"用户，用可用数据推导答案

### 改进方案

#### 方案 A：年份匹配验证（效果好）

在检索层增加年份过滤：

```python
def _filter_by_year(chunks: list[RetrievedChunk], query: str) -> list[RetrievedChunk]:
    """如果 query 明确指定年份，过滤掉不匹配的 chunks。"""
    query_years = set(re.findall(r'(20\d{2})', query))
    if not query_years:
        return chunks
    
    filtered = []
    for chunk in chunks:
        chunk_years = set(re.findall(r'(20\d{2})', chunk.section_path or ''))
        # 如果 chunk 有年份信息，必须匹配 query 的年份
        if chunk_years and not (query_years & chunk_years):
            continue
        filtered.append(chunk)
    
    return filtered
```

**优点**：从源头解决年份错位问题
**缺点**：可能过滤掉有用的对比数据

#### 方案 B：Prompt 年份检查（风险低）

在检查清单中增加年份验证：

```python
"□ 用户问题指定了年份吗？如果是，检索内容的年份是否匹配？\n"
"  - 不匹配时，必须明确说明「检索内容中没有{年份}年的数据」\n"
"  - 不要用其他年份的数据替代\n"
```

#### 方案 C：拒答示例增强

在 prompt 中增加更多拒答示例：

```python
"**问**：「2025年新能源产品收入是多少？」\n"
"**检索内容**：只有2024年新能源收入40.25亿元\n"
"**正确**：「检索内容中没有2025年新能源产品收入的数据，只有2024年的数据（40.25亿元）。」\n"
"**错误**：「2024年新能源产品收入为40.25亿元...」← 年份不匹配，不应该回答\n"
```

### 推荐方案

**组合使用**：方案 A（年份过滤）+ 方案 B（prompt 检查）+ 方案 C（示例增强）

### 验证标准

- Q55/Q59 得分从 0-1分提升到 2-3分
- I类整体从 2.00/3 提升到 2.5+/3
- 不误杀正确回答（如跨年份对比问题）

## 阶段三：C类跨文档对比（预计 2-3 天）

### 问题分析

**当前状态**：1.88/3（从 1.50 提升 25%，但仍是弱项）

**典型案例**：
- Q17-Q24：跨年份对比问题，LLM 经常只回答部分年份的数据
- 根因：检索到的 chunks 年份覆盖不全，或者 LLM 没有综合所有文档

### 改进方案

#### 方案 A：年份覆盖度检查（效果中）

在检索层检查年份覆盖度：

```python
def _check_year_coverage(chunks: list[RetrievedChunk], query: str) -> bool:
    """检查检索结果是否覆盖了 query 要求的所有年份。"""
    query_years = set(re.findall(r'(20\d{2})', query))
    if not query_years:
        return True
    
    covered_years = set()
    for chunk in chunks:
        chunk_years = set(re.findall(r'(20\d{2})', chunk.section_path or ''))
        covered_years.update(chunk_years)
    
    missing_years = query_years - covered_years
    if missing_years:
        logger.warning(f"Missing years in retrieval: {missing_years}")
        # 触发补充检索
        return False
    return True
```

#### 方案 B：多文档综合 prompt（效果中）

在 prompt 中强调多文档综合：

```python
"## 多文档综合（强制规则）\n"
"当问题涉及多个年份/文档时：\n"
"1. 在 <think> 中列出每个年份对应的 Source\n"
"2. 检查是否所有年份都有对应的数据\n"
"3. 回答时逐一列出每个年份的数据，标注来源\n"
"4. 如果某个年份数据缺失，明确说明\n"
```

#### 方案 C：强制每文档至少一个 chunk（已实现）

`_truncate_with_doc_diversity()` 已经确保每个文档至少保留一个 chunk。

### 推荐方案

**组合使用**：方案 A（年份覆盖度检查）+ 方案 B（多文档综合 prompt）

### 验证标准

- Q17-Q24 平均得分从 1.5分提升到 2.0+分
- C类整体从 1.88/3 提升到 2.3+/3

## 风险评估

### 高风险
1. **Prompt 改动导致 LLM 行为剧变**
   - 缓解：每次改动后立即评测，小步快跑
   - 缓解：保留 prompt 版本，可以快速回滚

2. **检索层改动影响其他类别**
   - 缓解：改动前记录基线分数
   - 缓解：改动后立即跑全量评测

### 中风险
1. **年份过滤过于严格**
   - 缓解：只在 query 明确指定年份时启用
   - 缓解：保留对比数据的检索能力

2. **反面证据检索增加延迟**
   - 缓解：只在检测到趋势断言时启用
   - 缓解：限制反面证据的数量

### 低风险
1. **Prompt 示例增强**
   - 影响：增加 prompt 长度，可能影响 token 预算
   - 缓解：精简示例，控制在合理长度
